# Jira Bug 修复工作流

> 端到端 Jira Bug 修复流程，阶段 1～6 只读不写。默认手动模式，阶段间需用户确认。
>
> **前提**：mcp-atlassian 已配置且 PAT 有效；Git 环境正常。
> **输出规范**：Markdown 结构化（标题/列表/表格/代码块），代码引用用 `startLine:endLine:filepath`；容易 → 精简，困难/极难 → 详细。
> **格式参考**：各阶段输出模板见 [reference.md](reference.md)。

## 触发词与模式

| 说法示例 | 模式 | 说明 |
|---------|------|------|
| 「修复这个 bug [URL]」「帮我修复 [URL]」`jira-fix [URL]` | 👤 手动 | 默认，方案/计划/提交需用户确认 |
| 「自动修复 [URL]」「修复 [URL] 自动模式」`jira-fix [URL] --auto` | 🤖 自动 | 全流程自动执行，无需确认 |
| 「强制修复 [URL]」「跳过分级修复 [URL]」`jira-fix [URL] --force` | 🤖 自动 | 跳过难度分级，强制自动执行 |
| 「继续修复 [URL]」「再次修复 [URL]」`jira-fix [URL] --retry` | 👤 手动 | 跳过阶段0/1，从**阶段3**重新分析（修复不完整时使用） |
| 「从上次继续」「恢复修复 [URL]」`jira-fix [URL] --resume` | 当前模式 | 从断点恢复（中途中断时使用） |

**模式识别规则**：触发词中含「自动」「--auto」→ 自动模式；含「强制」「跳过分级」→ 跳过分级（自动模式）；含「继续修复」「再次修复」「--retry」→ 阶段3重入（修复迭代）；含「从上次继续」「恢复」「--resume」→ 断点恢复；其余默认手动模式。

## 模式差异速查

| 阶段 | 🤖 自动模式 | 👤 手动模式 |
|------|------------|------------|
| 阶段0：前置检查 | P0 自动拦截，工作区自动 stash | P0 提示，工作区提示用户处理 |
| 阶段2：理解对齐 | 跳过，直接进入阶段3 | 复述理解 + 列歧义点，等用户确认后进入阶段3 |
| 阶段4：难度分级 | 极难 → 终止，输出标记报告 | 极难 → 列出风险，用户选择 A/B |
| 阶段5：探索与审查方案 | AI 自动探索并**循环审查**（≤3轮），通过后自动进阶段6；超限暂停（批量模式标记跳过） | 输出方案表→用户选择→审查→用户判定通过/不通过→循环至通过后进阶段6 |
| 阶段6：制定计划 | 自动确认，直接进阶段7 | 等用户确认 |
| 阶段7：执行计划 | 前置创建分支 + 执行 + Linter + 自动生成分析报告 | 单工程：直接创建分支，无需确认；多工程：展示分支计划后确认创建 + 执行 + Linter |
| 阶段8：检查验证 | 自动判定通过/未达标；未达标自动回退（最多 2 次，超限暂停） | 等用户确认通过后进入阶段9 |
| 阶段9：提交 PR/MR | 自动 push + 创建 PR/MR | 展示提交计划，用户确认后 AI 执行 push + 创建 PR/MR |
| 阶段10：Review 与合并 | ⛔ **停在阶段9出口**，等用户完成 Code Review 并确认合并，AI 合并、清理分支、回写 Jira | PR/MR 已在阶段9创建，等待 Code Review，用户确认后 AI 合并、清理分支、回写 Jira |
| 中断恢复 | 自动恢复，不询问 | 询问是否恢复 |

## 模式生命周期

> 自动模式的进入、持续与退出规则，避免模式粘滞导致用户未察觉的自动决策。

> 核心规则（自动恢复手动 / 显式重进 / 隐式延续不激活 / 批量场景）由强依赖 skill `workflow-mode-lifecycle` 承载（前置检查已保证可用），本节不再内联重复。jira-fix-workflow 特有说明：「全流程完成」= 正常完成阶段 0-10 全流程（无论收尾即 PR 合并完成，还是中间任一阶段的最终终止）；失败终止、极难终止、用户主动停止、审查超限暂停后用户介入终止均视为流程中断，恢复手动。重新进入自动模式须**显式触发**（如「自动修复 [URL]」「jira-fix [URL] --auto」「切换自动模式」）；隐式延续（如「继续修复」「再改一下」）**不会**重新激活自动模式。

### 特有差异

| 场景 | 模式行为 |
|------|---------|
| 阶段 9 完成（PR 已创建） | 恢复手动；阶段 10 本身就需用户确认合并 |
| 阶段 10 合并完成 | 恢复手动 |
| 阶段 8 验证未达标回退 | 保持当前模式（自动模式回退≤2 次内仍自动；超限恢复手动） |
| `--retry`（阶段 3 重入） | **重置为手动模式**（用户已介入判断需重新分析） |
| `--resume`（断点恢复） | **沿用断点时的模式**（不重置，意图是"从中断点继续"） |
| 极难终止（自动模式） | 恢复手动 |

## 通用原则

- **先调查再发言**：没有代码证据不做判断，以事实而非猜测说话
- **⚠️ 主动提问**：遵循 `clarifying-question-discipline`（一次一问、多轮问清）。
- **Jira 状态边界**：研发角色只流转到「已修复」；关闭、验证通过等状态由 QA 角色流转

## 路径选择

> 阶段 4 难度分级后，根据等级选择执行路径。路径可升级不可降级。

| 路径 | 适用等级 | 要求 |
|------|---------|------|
| 精简路径 | 🟢 容易 | 精简输出：方案可 1 个 + 风险说明，计划可合并。阶段 8 和 9 不可跳过 |
| 标准路径 | 🟡 中等 | 阶段 1～10 全部执行，方案和计划按标准格式 |
| 完整路径 | 🟠 困难 / 🔴 极难（选 B） | 阶段 1～10 全部执行；优先使用 `brainstorming` 类增强能力；阶段 7 执行后暂停等审查 |

执行中发现范围扩大时必须升级路径：精简 → 标准，标准 → 完整。手动模式下升级需用户确认。

## 状态持久化（中断恢复）

**恢复**：检测到 state.json 时，**[🤖 自动]** 直接从 `current_phase` 继续；**[👤 手动]** 询问是否恢复。**清理**：完成后 state.json 设 `current_phase: "completed"`。

**继续修复（阶段3重入）**：触发词含「继续修复」「--retry」时，跳过阶段0/1，直接从阶段3重新分析。执行逻辑：
1. 读取已有 `01-jira-info.md` 作为 Jira 上下文，不再调用 API
2. 询问用户：「上次修复了什么？本次发现的新现象是？」（一次性收集补充上下文）
3. 将补充上下文写入 `02-analysis.md` 顶部的「本次迭代背景」区块，再重新执行分析
4. 重置 state.json：`current_phase: 3`，`completed_phases: [0, 1]`，清空 `grade / selected_option / review_round / review_status`
5. 阶段7前置创建分支时，在原分支名加 `-v2`（`-v3`、`-v4`……以此类推）
6. **`--retry` 打点调试首选**：重新分析完成后，若根因仍不够清晰，优先触发「🔬 打点调试」而非再次纯静态分析——上一轮已验证静态分析的边界，运行时数据是更高效的下一步

```

├── 01-jira-info.md      ← 阶段1输出

├── 04-grade.md          ← 阶段4难度分级结果
├── 03-options.md        ← 阶段5输出（含方案对比 + 审查循环记录）
├── 04-plan.md           ← 阶段6输出
├── 05-execution.md      ← 阶段7输出

```

### state.json 结构

```json
{
  "jira_id": "YNOTR-12345",
  "jira_url": "https://your-jira.example.com/browse/YNOTR-12345",
  "mode": "manual",
  "current_phase": 3,
  "completed_phases": [0, 1],
  "branch": "fix/jira-fix-YNOTR-12345",
  "grade": null,
  "selected_option": null,
  "review_round": 0,
  "review_status": null,
  "enhanced_capabilities": {},
  "started_at": "ISO_TIMESTAMP",
  "last_updated": "ISO_TIMESTAMP"
}
```

**审查相关字段说明**：
- `review_round`：`0` = 未开始审查，`1`-`3` = 第 N 轮审查（自动模式上限 3），用户说「继续审查」后可追加
- `review_status`：`null` = 未开始，`"in_progress"` = 审查中，`"passed"` = 审查通过，`"failed_max_rounds"` = 达到上限未通过

**环境能力探索字段说明**：
- `enhanced_capabilities`：阶段0完成后扫描的增强能力映射。key 为能力类型（如 `"debug"`、`"test"`、`"verify"`），value 为匹配到的 skill/agent 名称。空对象 `{}` 表示未探索或未发现增强能力

## 阶段0：前置检查

> 任一检查失败则中断流程

### 执行步骤

1. **识别模式**：解析触发词，识别 `--manual` / `--force` / `--resume`，写入 state.json
2. **mcp 连通检查**：调用 `jira_get_issue`（仅获取标题/优先级）；失败立即终止，提示检查配置/PAT/URL/网络
3. **P0 拦截**（仅自动）：优先级为 P0 → 终止，提示改用手动模式
4. **Git 检查**：**[🤖]** 工作区不净 → 自动 stash；**[👤]** 工作区不净 → 提示用户处理

### 输出字段

Jira ID、Issue 标题、优先级、执行模式、mcp 状态、Git 状态。

**[👤 手动 / 🤖 自动]** 直接进入阶段1：读取 Jira 信息，无需确认。

## 阶段1：读取 Jira 信息

### 原则

- 优先获取最新数据（`--live` 模式）
- API 不可用时读取本地缓存
- 复用 `jira-read` skill 的统一逻辑
- **工具限制**：✅ mcp-atlassian API / jira-read；❌ Edit/Write/Bash

调用 `jira-read {JIRA-ID} --live`，降级读本地缓存，再降级手动提供/报错终止。保存到 `.jira-fix/{JIRA-ID}/01-jira-info.md`，更新 state.json。

**提取**：Jira ID、标题、优先级、状态、描述、复现步骤、期望/实际结果、附件、评论。

### 输出字段

Jira ID、标题、优先级、状态、数据来源、问题描述、复现步骤、期望/实际结果、评论摘要。

## 阶段2：理解对齐

> 原则：基于阶段1读取的 Jira 数据，用自己的话复述理解，暴露歧义点和关键假设；在进入技术分析前与用户对齐。**禁止读取代码库。**

### 输出格式

```
【歧义与假设】（若有）
[问题] A [...] B [...]

```

## 阶段4：难度分级 + 模式决策网关

> 基于阶段3的分析结果，使用规则制判定难度等级，决定后续行为

### 🔴 极难触发条件（满足任一即为极难）

| 条件 | 判断依据 |
|------|---------|
| 根因未知 | 分析后仍无法定位根本原因（知道大概模块但无法定位到具体逻辑） |
| 涉及架构变更 | 需要重构模块间通信、变更设计模式、调整核心数据结构 |
| 涉及数据迁移 | 需要数据库 schema 变更或数据格式迁移 |
| API 协议变更 | 需要修改对外接口签名，影响调用方 |
| 改动范围过大 | 预估改动文件 >10 个 或 预估行数变更 >500 行 |
| 跨仓库/跨服务 | 需要在多个独立 Git 仓库中协同修改 |

### 等级判定（未命中极难条件时）

- 预估文件 ≤ 3 个，根因**清晰** → 🟢 **容易**
- 预估文件 4–10 个，根因**基本清晰** → 🟡 **中等**
- 预估文件 ≤ 10 个，根因**较清晰**但改动较多 → 🟠 **困难**

### 模式 × 等级 → 行为

| 等级 | 🤖 自动模式 | 👤 手动模式 |
|------|------------|------------|
| 🟢 容易 | ✅ 正常执行 | 💡 提示「此问题较简单，可切换自动模式」，继续手动流程 |
| 🟡 中等 | ✅ 正常执行 | 💡 提示「此问题风险可控，可切换自动模式」，继续手动流程 |
| 🟠 困难 | ✅ 执行，阶段7完成后暂停等用户审查代码再提交 | ✅ 正常手动流程 |
| 🔴 极难 | ❌ **终止**，输出标记报告 | ⚠️ **风险提示**，用户选择 A/B |

### 输出字段

难度等级（🟢/🟡/🟠/🔴）、命中条件列表、行为提示（终止报告/风险选项 A-B/建议切换模式）、后续行动建议。分级结果保存到 `.jira-fix/{JIRA-ID}/04-grade.md`，更新 state.json `"grade"` 字段

**路径选择**：基于分级结果，按「路径选择」节的规则选择执行路径，在输出中声明所选路径。

**[👤 手动]** 非极难时：分级结果已追加到阶段3输出，不再单独停顿，直接由阶段3出口的 ⏸️ 统一等待用户确认。
**[👤 手动]** 极难选 B（继续）时，附上：「⚠️ 已知晓高风险，进入**阶段5：探索与审查方案**，回复「确认」继续，或回复「A」终止。」
**[🤖 自动]** 自动进入阶段5，无需用户确认。

- 偏离计划修改了计划外文件，未说明原因
- **[🤖 自动]** 遇到计划外问题未暂停，自行决策继续
- 执行完成未输出执行报告直接进入阶段8

## 阶段8：检查验证

> 原则：只输出检查结果，不修改代码；若验证未达标，按失败类型决定返回路径

**🔌 增强能力集成**：若发现「✅ 完成验证」类能力（如 `verification-before-completion`、OMC `verifier` agent），在验证环节调用（运行测试、确认修复、检查回归），**有证据再提交**。

### 验证维度

1. **目标达成验证**：对照阶段1读取的 Jira 复现步骤和期望结果，逐项确认问题是否已被修复
2. **与计划对比**：与阶段6的文件修改清单对比，确认所有修改项均已完成
3. **测试执行**：
   - **有自动化测试**：运行相关测试用例（`npm test`、`pytest`、`go test` 等），将结果纳入结论
   - **无自动化测试**：按 Jira 复现步骤描述手动验证路径，列出验证要点提示用户
4. **副作用检查**：确认 Node 版本已按项目声明对齐（见 `node-version-discipline`）、Linter 和 TypeScript 检查均通过（补充确认阶段7结果），检查改动是否在其他模块引发新问题
5. **逻辑完整性**：修复点是否完整覆盖根因，有无遗漏边界条件
6. **调试-验证闭环**：若阶段 3 用了调试 skill 定位根因，按 `analysis-core` §4 用**同一 skill** 验证修复（而非只跑测试）

### 验证结论（二级制）

| 结论 | 判定标准 | 后续动作 |
|------|---------|---------|
| ✅ **通过** | 问题已修复，测试通过，无新副作用 | 进入阶段9：提交 PR |
| ❌ **未达标** | 问题仍存在、新副作用未解决或测试失败 | 按失败类型决定返回路径 |

**未达标返回路径**：

| 失败类型 | 返回阶段 |
|---------|---------|
| 代码实现有误（方向正确但执行有缺陷） | 阶段7 重新执行 |
| 方案设计有缺陷（测试暴露更深层问题） | 阶段5 重新审查/选方案 |
| 根因分析不完整（问题范围比预期更大） | 阶段3 补充分析 |

### [🤖 自动模式] 验证循环

- AI 自动判定通过/未达标
- **未达标时**：按上方返回路径自动回退，输出回退原因
- **回退上限**：2 次；超过上限暂停，等用户介入决策

### [👤 手动模式] 验证确认

- AI 输出验证结果后停止，等用户响应：
  - 用户说「通过」「确认」「OK」→ 进入阶段9：提交 PR
  - 用户说「返回修复」「重新执行」→ 回到阶段7
  - 用户说「重选方案」→ 回到阶段5

### 输出格式

### 验证报告诚实原则

按 `pdca-review-orchestration` 的验证报告诚实规则标注每项结果。

```
【验证结果】
- Jira 复现步骤验证：（逐项列出 ✅ 已修复 / ❌ 仍存在）
- 与阶段6计划对比：已完成 ... / 未完成 ...（如有）
- 测试结论：（已运行 → 附结果；无自动化测试 → 列手动验证要点）
- 副作用检查：Node(声明版本 vX) ✅/⚠️ 未对齐，Linter ✅/❌，TS ✅/❌，功能副作用 ✅/❌
- 逻辑完整性：...
- 验证结论：✅ 通过 / ❌ 未达标（未达标需说明返回路径及原因）
```

保存到 `.jira-fix/{JIRA-ID}/06-verification.md`，更新 state.json。

**工具限制**：✅ Bash（仅运行测试命令）；❌ Edit/Write

> ⛔ **[手动模式 — 阶段8 出口]** 输出验证结果后**立即停止**，在结果末**必须附上**：
> - [✅ 通过]：「⏸️ 阶段8（检查验证）通过。是否进入**阶段9：提交 PR**？回复「确认」继续。」
> - [❌ 未达标]：「⏸️ 验证未通过。建议返回 阶段X（原因：...）。回复「确认」同意返回，或指定其他处理方式。」
> 🤖 **[自动模式]** AI 自动判定通过/未达标；通过进入阶段9；未达标按返回路径自动回退（上限 2 次，超限暂停）。

### Red Flags — 禁止行为

- 跳过检查验证，代码修改完成后直接进入阶段9提交（未经验证的修复不可提交）
- 检查验证阶段修改代码（违反只读约束）
- 测试失败或问题仍存在，但仍判定「通过」推进提交
- **[👤 手动]** 用户未明确确认通过，AI 自行推进到阶段9
- **[🤖 自动]** 未达标回退超过 2 次仍不暂停
- 未达标时未说明返回路径直接终止

## 阶段9：提交 PR/MR

**🔌 增强能力集成**：
- 若发现「✅ 完成验证」类能力（如 `verification-before-completion`、OMC `verifier` agent），在提交前执行独立验证（运行测试、确认修复、检查回归），**有证据再提交**
- 若发现「📋 代码审查」类能力（如 `requesting-code-review`、OMC `code-reviewer` agent），提交后自动发起代码审查
- 未发现以上能力则按原有流程执行

### [🤖 自动模式] 自动提交

1. 收集提交信息（Jira ID、根因、修复方案、修改文件、报告路径）
2. 调用 `git-commit` SKILL（execute=true，自动模式）：自动 add / commit / push
3. **创建 PR/MR**：push 成功后，根据 `git remote -v` 判断平台（URL 含 `github.com` → `gh pr create`；含 `gitlab` → `glab mr create`），标题格式与 commit message 保持一致；描述必须包含根因、修复方案、修改文件清单、验证场景（功能/边界/回归各 ≥2）、Jira 链接

**PR/MR 描述字段**：修复分支、Commit、根因、修复方案、修改文件、分析报告路径、验证场景（功能/边界/回归各 ≥2）。

### [👤 手动模式] 确认后提交

收集提交信息，展示将要执行的 commit 计划（分支、commit message、修改文件、验证场景各 ≥2 条），等用户确认后，**AI 执行** add / commit / push + 创建 PR/MR。

> ⛔ **[手动模式 — 阶段9 出口]** 展示提交计划和验证场景后**立即停止**，在末尾**必须附上**：
> 「⏸️ 提交计划已就绪。确认后 AI 将执行 push + 创建 PR/MR。回复「确认」继续，或告知需要修改。」
> 🤖 **[自动模式]** 无需确认，自动执行 push + 创建 PR/MR。

### Commit Message 格式

```
<type>(<scope>): <Jira-ID> <subject>
```

示例：`fix(ai-summary): YNOTR-12167 修复分享链接中AI摘要按钮显示问题`

**Type**：fix、feat、refactor、perf、style、docs、test　**Scope 示例**：ai-summary、share、auth、api、ui、core

### 完成输出字段

修复分支、Commit Hash、推送状态、**PR/MR URL**、分析报告路径；多项目时用表格。

保存到 `.jira-fix/{JIRA-ID}/07-report.md`

### Red Flags — 禁止行为

- **[👤 手动]** 未等用户确认直接执行 git push
- Commit message 遗漏 Jira ID
- 多项目场景只提交了部分项目
- PR/MR 创建失败后未输出警告直接进入阶段10

## 阶段10：Review 与合并

> PR/MR 已在阶段9创建，等待 CI + Code Review，完成合并、分支清理与主分支同步

**🔌 增强能力集成**：若发现「📋 代码审查」类能力（如 `requesting-code-review`、OMC `code-reviewer` agent），可辅助推进正式 Code Review 流程。

### [🤖 自动模式 / 👤 手动模式] 确认后合并

> **两种模式行为完全一致**：PR/MR 合并是不可逆操作（受保护分支无法强推回退），即使在自动模式下也**必须等用户确认**后才执行。

1. 展示 PR/MR URL（来自阶段9 `07-report.md`）和描述摘要，**立即停止，等用户完成 Code Review 并确认合并**
2. 用户确认（说「合并」「merge」「确认」「OK」等）后，AI 依次执行：

   #### 步骤 2.1：合并纪律（merge-discipline skill）

   > 合并动作执行前加载 `merge-discipline`，按 Part A → B → C → D 执行；合并前检查清单见 `merge-discipline/reference.md`。用户直接说 merge 也必须加载，不得隐式跳过。

   #### 步骤 2.2：执行合并

   - 合并：**GitHub** `gh pr merge --merge`；**GitLab** `glab mr merge`（参数与团队策略一致）
   - 删除远程修复分支：`git push origin --delete fix/jira-fix-[JIRA-ID]`
   - 切换并同步默认分支：`git checkout <默认分支> && git pull origin <默认分支>`（`main`/`release/*` 等，从 `release-branch` 文件或 `git remote show origin` 获取）
   - 删除本地修复分支：`git branch -d fix/jira-fix-[JIRA-ID]`

   #### 步骤 2.3：Jira 状态回写（合并完成后）

   PR/MR 已成功合并，代码已进入主分支，此时回写 Jira 状态准确反映修复已合入。

   **两步独立调用**：① `jira_get_transitions` + `jira_transition_issue` 流转状态（不传 `comment` 参数）；② **独立调用** `jira_add_comment(issue_key=..., body=...)` 写修复评论。`jira_add_comment` 的评论内容参数名为 `body`（非 `comment`）。

   流转到「已修复」；后续的关闭、验证通过等状态由 QA 角色流转；无匹配时跳过记警告。

   **修复评论字段**：修复分支、Commit、PR/MR URL、根因、修复方案、修改文件、分析报告路径、验证场景（功能/边界/回归各 ≥2）。

   **错误处理**：回写失败不阻断流程，仅输出警告并记录到报告。

> ⛔ **[阶段10 出口 — 自动模式 & 手动模式]** 展示 PR/MR URL 后**立即停止**，在末尾**必须附上**：
> 「⏸️ PR/MR 已在阶段9创建，请完成 Code Review。确认合并后回复「确认」，AI 将执行合并并清理分支。」
> ⚠️ **[自动模式禁止行为]** 禁止在未收到用户合并确认前自行调用 `gh pr merge` / `glab mr merge`。合并到受保护分支后无法强推撤销，必须走 revert commit 流程，风险极高。

### 完成输出字段

合并状态、分支清理状态（本地/远程）、主分支同步状态、**Jira 回写状态**（PR/MR URL 已在阶段9 `07-report.md` 中记录）。保存到 `.jira-fix/{JIRA-ID}/08-merge.md`，同时更新 state.json `current_phase: "completed"`。

### Red Flags — 禁止行为

- **[🤖 自动模式 / 👤 手动模式]** 未等用户确认合并直接执行 `gh pr merge`、`glab mr merge` 等平台合并命令——**自动模式同样禁止**，合并是不可逆操作
- CI 未通过时强制合并（不加 `--admin` 或 `--force`）
- 合并后未清理本地和远程修复分支
- 合并后未同步主分支
- **合并前覆盖率门控脚本崩溃 / 无报告 / 退出码 1 却继续合并**——崩溃必须视为门控未通过，暂停等用户，不得误判为「覆盖率通过」
- **覆盖率报告显示不达标，自动模式强行合并**——不达标必须暂停等用户决策（强制合并/补测试/放弃）
- **用户显式跳过门控但未在 `08-merge.md` 和 PR 描述留痕**——跳过必须留痕，否则事后无法追溯门控被跳过
- **未显式指定 `--base` 且未输出「MR 场景可能误判为 0 变更」警告**——`--base` 获取失败时的降级警告必须呈现给用户
- **修复/docs push 后裸 merge（无 `--sha`、无合入后祖先校验）**——刚 push 的提交未入目标分支（见 `merge-discipline` Part D）
- **把刚 push 后立即出现的「Pipeline succeeded」当当前 tip 已绿**——多半是旧 tip 结果（见 `merge-discipline` Part D step 2）
- **Jira 回写时通过 `jira_transition_issue` 的 `comment` 参数传评论**（该参数不可靠，必须独立调用 `jira_add_comment`）
- **Jira 回写失败后未输出警告，静默跳过**

## 安全机制（自动模式）

修改前自动 stash；**警告阈值**：>10文件 或 >500行；**阻断阈值**：>20文件 或 >1000行（需 `--force` 解除）；Linter 错误自动阻断；**审查循环上限**：3 轮（超限暂停或标记跳过）；记录所有自动决策日志。

## 常见错误

> 只记本 skill 非直觉陷阱。阶段工具约束 / 审查循环上限 / Linter 等见上文；增强能力 → `env-capability-discovery`；合并 tip → `merge-discipline`。不复述正文已写明的规则。

| 错误 | 后果 | 修正 |
|------|------|------|
| **[👤 手动]** 跳过阶段2直接进入阶段3分析 | 带着错误理解做技术分析 | 手动模式须先完成理解对齐并获用户确认 |
| **[👤 手动]** 阶段2中读取代码库 | 混淆理解对齐与技术分析 | 阶段2仅基于 Jira 数据，禁止代码探索 |
| 存在性验证为「不存在/描述不符」仍继续 | 方向全错 | 立即停并写 Jira 评论，等用户确认 |
| 跳过行业通病评估，或「无可行解」仍进方案阶段 | 为无解问题烧修复资源 | 通病为门控（见 `known-issue-research`）；无可行解则写报告+Jira 评论后中断 |
| 根因是上游依赖 bug 却堆 workaround、不查 Changelog | 错过一行升级即可修 | 加载 `upstream-dependency-debug` 走 4 步决策 |
| 自动模式遇极难仍继续执行 | 高风险改动失控 | 触发阶段4网关，终止流程 |
| 代码改动缺少 `// fix [JIRA-ID]` 注释 | CR 难以定位修复点 | 每处改动附近必须标注 |
| **[🤖 自动]** 验证未达标回退超过 2 次不暂停 | 无限循环 | 超过 2 次回退必须暂停等用户 |
| **[🤖 自动]** 未等用户确认直接合并 | 受保护分支难以强推撤销 | 自动与手动一致：**确认后再合并** |
| 用 `jira_transition_issue` 的 `comment` 传评论 | 评论被静默丢弃 | 独立调用 `jira_add_comment` |
